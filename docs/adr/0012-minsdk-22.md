# ADR-012 — Mantener `minSdkVersion` en 22, no subir a 26

- **Estado:** Aceptada
- **Fecha:** 2026-08-11
- **Decide:** Arquitectura de software
- **Sustituye a:** ninguno. Desvía de `CLAUDE.md` §5 y del documento SC-ARQ-2026-001 §2.1.

## Contexto

`CLAUDE.md` especifica `minSdkVersion 26` (Android 8.0) y el documento de
arquitectura lo justifica diciendo que ese es «el piso del parque de dispositivos
objetivo».

La app publicada declara **`minSdkVersion 22`** (Android 5.1), según
`coffee-check-app-main/android/variables.gradle`. Es decir: el piso real ya está
cuatro niveles de API por debajo de lo que el documento asumía, y hay usuarios
instalados ahí.

Al mismo tiempo, `PRESERVE.md` §3 declara invariante que el `minSdk` publicado no
sube sin análisis de impacto. Las dos normas del propio proyecto se contradicen, y
hay que resolverlo explícitamente en lugar de dejar que lo decida quien escriba
primero el `build.gradle.kts`.

## Decisión

Se mantiene `minSdkVersion 22`.

Las capacidades que exigen una API superior se detectan y degradan en tiempo de
ejecución, no se imponen desde el manifiesto.

## Alternativas consideradas

**Subir a 26, como dice `CLAUDE.md`.** Descartada. Subir el `minSdk` de una app
publicada no produce ningún aviso: los dispositivos por debajo del nuevo mínimo
simplemente dejan de ver la actualización en Play, en silencio y para siempre. El
usuario no puede hacer nada al respecto y ni siquiera se entera de que existe una
versión nueva.

Y el hardware que se abandonaría es exactamente el que el documento describe como
público objetivo: gama baja Xiaomi, Tecno, Infinix, Samsung serie A, «Android
8–13» según §2.1 — pero el `minSdk 22` publicado sugiere que el equipo ya
encontró usuarios por debajo de esa franja, o no habría bajado el mínimo.

**Subir a 24 como término medio.** Descartada por lo mismo, en menor grado. Un
término medio sin datos no es un análisis de impacto, es una corazonada con
apariencia de prudencia.

**Subir a 26 con una versión de mantenimiento congelada para API 22–25.**
Descartada: exige mantener dos ramas de una app que aún no tiene equipo para
mantener bien una sola.

## Consecuencias

**Positivas**
- Ningún usuario actual pierde la ruta de actualización.
- Se respeta el invariante de `PRESERVE.md`, que es el que gobierna un refactor
  sobre base publicada.

**Negativas — asumidas conscientemente**

1. **Desugaring obligatorio.** `java.time` y parte de `java.util.stream` no
   existen antes de API 26. Se activa `isCoreLibraryDesugaringEnabled` en los
   plugins de convención, con `desugar_jdk_libs`. Coste: ~200 KB en el APK y algo
   más de tiempo de compilación.
2. **NNAPI no está disponible por debajo de API 27.** La estrategia de delegates
   ya contempla el respaldo a CPU con cuatro hilos (§7.3), pero en API 22–26 ese
   respaldo deja de ser excepción y pasa a ser la ruta normal. **La latencia p95
   de 900 ms del RNF hay que medirla en un dispositivo API 22 real**, no solo en
   el Snapdragon 680 de referencia. Si no se cumple ahí, se reabre este ADR con
   datos en la mano.
3. **Superficie de prueba mayor.** El conjunto de dispositivos de prueba tiene que
   incluir al menos uno con Android 5.1 o 6.
4. Algunas APIs de AndroidX exigen comprobación de versión en tiempo de ejecución
   donde con `minSdk 26` no haría falta.

## Condición de revisión

Se reabre este ADR cuando ocurra cualquiera de estas tres cosas:

1. **Play Console → Estadísticas → Dispositivos activos por versión de Android**
   muestre menos del 2 % de la base instalada por debajo de API 26 durante tres
   meses seguidos.
2. La latencia p95 de inferencia en un dispositivo API 22 real supere los 900 ms
   y no haya forma de bajarla sin NNAPI.
3. Una dependencia imprescindible eleve su propio `minSdk` por encima de 22.

En los tres casos, la decisión se toma **con el dato de Play Console delante**, no
por comodidad de desarrollo.
